# 004. 복구 배치에서 PG별 처리 기회 분배

- 상태: 채택
- 기록일: 2026-10-26
- 관련 이슈·PR: 로드맵 #1 후속, API 계약 전 준비 작업

## 해결하려던 문제

기존 환불·보상 요청 조회는 오래된 REQUESTED부터 전체 limit만큼 선택했다. 한 PG에 limit 이상의
실패 요청이 쌓이면 매 회차 같은 요청이 선택되어 다른 PG의 정상 요청도 배치에 들어오지 못할 수 있다.
단일 배치 안의 오류 격리만으로는 이 문제를 해결하지 못한다.

## 결정

2026-10-26 작업 담당자가 전체 상한 유지·PG별 기회 분배 추천안을 승인했다.

- 각 복구 작업의 기존 전체 batch-size 상한을 유지하고 PG별 처리 기회를 나눈다.
- 각 PG 안에서는 requested_at·id 순서를 유지한다. 다른 PG가 사용할 몫이 없으면 남은 용량을 쓴다.
- 상한이 1이거나 홀수인 경우의 우선 PG를 회차마다 바꿔 특정 PG가 계속 밀리지 않도록 한다.
- 요청의 원래 requested_at, 멱등 키, PG, 금융 상태는 바꾸지 않는다.
- 환불·보상 조회 각각에 독립된 메모리 커서를 두고 최초 TOSS부터 조회 우선 PG를 순환한다.
  재시작하면 초기화되며 인스턴스 간 커서는 공유하지 않는다.
- SQL의 PG별 ROW_NUMBER로 대상 순번을 매기고 순번·회차 우선 PG로 정렬한 뒤 기존 LIMIT를 적용한다.
  한 PG에 잔여 요청이 없으면 다른 PG의 다음 순번이 선택되어 남은 용량을 채운다.

## 선택 이유

API 계약이나 외부 PG의 재시도 규칙을 추측하지 않고도 한 PG의 장애가 다른 PG 복구를 계속 막는
현상을 줄일 수 있다. 전체 실행량 상한과 기존 요청 자체를 보존한다.

## 검토한 대안

- PG마다 기존 batch-size 전체를 허용한다. PG별 처리 기회는 확보되지만 한 회차 최대 호출량이 늘어난다.
- 실패 요청에 backoff를 적용한다. 별도의 시각·횟수 저장과 재시도 간격 정책이 필요하며 이 결정에 포함하지 않는다.
- 현재 오래된 순서만 유지한다. 단일 PG의 실패 누적에 따른 다른 PG 처리 지연을 수용한다.

## 감수한 비용과 한계

PG 사이에서는 전체 생성 시각 순서보다 처리 기회 분배를 우선한다. PG 안의 순서는 유지한다.
타임아웃 값·backoff·재시도 종료 횟수는 정하지 않으며 장애 PG 복구 자체를 보장하지 않는다.
커서는 조회 호출마다 전진하고 트랜잭션 rollback에 맞춰 되돌리지 않는다. 다중 인스턴스의 전체적인
처리 순서를 보장하지 않으며, 반복 재기동 시 상한 1의 공정성이 유지되는 것도 보장하지 않는다.
윈도 함수는 eligible REQUESTED를 PG별로 정렬하므로 대량 누적 시 실행 비용을 관측해야 한다.
외부 승인·조회·취소 호출 수는 배치 행 수와 같다는 뜻이 아니며 기존 복구 로직을 따른다.

## 다시 검토할 조건

PG가 추가되거나 DB 공유 커서를 통한 다중 인스턴스 공정성, 외부 PG별 호출량 제한 또는 backoff 정책이
필요해질 때 검토한다.
