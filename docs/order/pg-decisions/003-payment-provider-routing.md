# 003. 결제 생성 시 PG 고정과 기존 결제 라우팅

- 상태: 채택
- 기록일: 2026-10-26
- 관련 이슈·PR: 로드맵 #1, PG 선택 #3 후속 (사용자 승인)

## 해결하려던 문제

전역 PG 설정을 바꾸면 기존 Toss 결제까지 새 PG에 조회·환불하게 될 수 있다.
설정 하나로 구현체를 제외하던 002의 구조는 기존 결제를 처리할 수 없다.

## 결정

2026-10-26 작업 담당자가 다음 전환 정책과 그 구현을 승인했다.

- 결제 생성 시 `payments.provider`에 `TOSS` 또는 `OWN`을 저장한다.
- 전환 전 결제는 상태와 무관하게 `TOSS`로 채운다. 이미 생성한 READY 결제도 Toss로 완료한다.
- 전역 선택은 새 결제 생성에만 적용한다. 기존 행의 PG를 변경하지 않는다.
- 결제창 설정·실패 코드 해석·승인·조회·환불·보상·재처리는 저장된 PG를 따른다.
- Toss 구현체는 신규 결제 선택과 무관하게 등록한다. 자체 PG 구현체는 외부 계약 확정 후 추가한다.
- 선택한 신규 PG 구현이 없으면 시작을 중단한다. 기존 결제의 PG 구현이 없거나 PG 식별자가
  없으면 해당 작업을 실패시키며 다른 PG로 대체하지 않는다.
- Toss로 되돌릴 때도 새 결제만 Toss로 만든다. 자체 PG 결제는 계속 자체 PG에서 처리하므로,
  그 구현체와 설정·인증 정보는 유지한다. 여기서 롤백은 설정 변경이며 옛 바이너리 배포가 아니다.

## 선택 이유

외부 결제의 소유 PG는 설정을 바꿔도 달라지지 않는다. 결제와 취소 이력을 옮기지 않고도
기존 결제 처리와 새 PG 도입, 신규 결제의 선택 복귀를 함께 지원한다.

## 검토한 대안

- 기존 결제가 모두 정리될 때까지 자체 PG 전환을 미룬다. 전환 시점을 기존 환불 기간에 묶는다.
- 기존 결제도 전역 설정을 따른다. 새 PG가 모르는 결제를 조회·환불하게 되어 채택하지 않는다.
- 결제 키 형식이나 생성 시각으로 PG를 추측한다. 결제 대기·재시도와 설정 복귀에 취약하다.

## 감수한 비용과 한계

이전 PG의 SDK·서버 구현과 정상 설정을 함께 유지한다. 기존 데이터는 Toss만 사용했다는 전제로
단일 ALTER에서 필수 컬럼·기본값·CHECK를 추가한다. 기본값은 기존 INSERT와 배포 호환성을 위한
TOSS이며 새 코드는 선택값을 명시한다. 공용 DB에는 별도 검토 절차로 적용한다.

자체 PG의 인증·상태·멱등성·결제창·웹훅 계약을 이 결정으로 만들지 않는다. 현재 구현체가 없으므로
`own`을 선택하면 시작하지 않는다. 자체 PG 결제가 생성된 후에는 provider를 모르는 옛 애플리케이션을
배포해서는 안 된다. 기존 전역 결제 키·멱등 키·거래 키 UNIQUE는 유지하며, 자체 PG 계약이 이 식별자
공간과 호환되는지는 실제 구현 전에 확인해야 한다.

## 다시 검토할 조건

기존 PG 처리를 종료할 수 있는 보존·환불·미완료 요청 조건이 확정되거나, 새 PG의 식별자 계약이
기존 UNIQUE와 충돌하거나, 다중 PG·가맹점 지원이 필요해질 때 검토한다.
