# 001. 결제창 PG 규칙의 Gateway 책임

- 상태: 채택
- 기록일: 2026-10-26
- 관련 이슈·PR: #2

## 해결하려던 문제

#2는 주문명 길이 제한과 사용자 취소 실패 코드 해석을 Gateway로 옮기도록 요구하지만,
제시된 인터페이스에는 이 책임을 수행할 메서드가 없다.

## 결정

2026-10-26 작업 담당자의 확인을 받아 `PaymentGateway`에 `formatOrderName(String)`,
`isUserCanceled(String)`, `isCardRejected(String)`을 추가한다.
서비스는 기존 주문명 구성과 실패 안내 문구를 유지하고, Toss 구현체는 100자 제한과
`PAY_PROCESS_CANCELED` 비교를 담당한다.

기존 `REJECT_CARD_COMPANY` 비교도 Toss 구현체의 `isCardRejected(String)`으로 옮긴다.
서비스의 실패 안내 문구와 분기 순서는 유지한다.

## 선택 이유

기존 결제창 조회 흐름을 유지하며 PG마다 다른 가공 규칙만 구현체에 둘 수 있다.

## 검토한 대안

별도 결제창 정책 인터페이스를 만들어 API 호출과 화면 입력 규칙을 분리할 수 있다.
이 경우 다음 PG 선택 작업에서 두 구현체의 조합을 일치시켜야 한다.

## 감수한 비용과 한계

이 결정은 API 호출과 결제창 입력 가공 책임을 하나의 인터페이스에 둔다.
이 결정은 자체 PG 상태 매핑, 조회 없음의 의미, 멱등성 계약을 정하지 않는다.
기존 결제의 PG 식별·라우팅과 Toss 롤백 정책도 정하지 않는다.
이 정책은 환불뿐 아니라 조회·미완료 보상에 영향을 주므로 자체 PG 활성화 전에 별도 합의가 필요하다.

## 다시 검토할 조건

자체 PG 결제창 계약에서 이 경계로 표현할 수 없는 규칙이 확인될 때 검토한다.
