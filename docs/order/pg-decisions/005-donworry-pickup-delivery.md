# 005. 결제와 독립된 P6 픽업 정보의 커밋 후 송신

- 상태: 로컬 구현 승인 범위, 팀 리뷰 대상
- 기록일: 2026-10-29
- 관련: DonWorry PR #334, P1 HMAC #219·#241

## 해결하려던 문제

P6는 주문번호·예정/실제 픽업 시각·상품명/수량이 필요하지만 CakeShop 송신부가 없었다.
결제 PG 연결을 기다리지 않고 사용자가 픽업 송신부 로컬 구현·검증을 요청했다.

## 결정

주문 스냅샷과 픽업 완료를 원 트랜잭션에서 이벤트로 알리고 커밋 이후 기존 P6 PUT 계약으로 보낸다.
별도 읽기 트랜잭션으로 저장된 원본 값을 읽고 P1 HMAC 규칙으로 실제 본문 바이트에 서명한다.
P6의 merchantId는 본문이 아니라 가맹점 코드·공유 키를 통한 인증 결과다.
기본 비활성이며 실제 운영 키·주소·배포 검증 전 자동 활성화하지 않는다.
이 결정은 PG 승인/취소 계약이나 다른 담당의 상태 전이를 변경하지 않는다.

## 선택 이유

P6는 픽업 선도착을 보관하고 후속 매입과 연결하므로 결제 HTTP 연동과 독립적으로 검증할 수 있다.
원 트랜잭션 안에서 HTTP를 보내면 롤백된 주문이 외부에 저장되거나 외부 지연이 주문 잠금을 오래 유지한다.

## 검토한 대안

- 주문 커밋 전 직접 HTTP: rollback 시 외부 기록만 남을 수 있어 제외.
- P5 결제 메시지에 픽업을 추가: 현재 픽업 전용 P6 계약과 다르며 결제 담당 범위를 바꾸므로 제외.
- outbox와 자동 재시도까지 도입: 영속 스키마·재시도 정책이 추가되므로 이번 로컬 구현에 포함하지 않는다.

## 감수한 비용과 한계

커밋 후 제한시간 내 동기 전송으로 응답이 잠시 지연될 수 있다.
실패나 커밋 직후 프로세스 종료의 자동 복구는 보장하지 않으며 운영용 영속 전달 이력은 후속이다.
주문·픽업 커밋은 유지하고 실패는 최소 로그로 기록한다. 실제 배포 테스트는 별도다.

## 다시 검토할 조건

운영에서 무손실 전달·자동 복구가 요구되거나 전달량이 증가할 때 outbox·재시도·비동기 전달 정책을 합의한다.
상세 설정·실패 범위는 ../donworry-pickup-delivery.md를 따른다.
